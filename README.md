# Мини-PDM: Состав изделия

Упрощённая PDM-система: импорт CAD-документов (JSON-экспорт), хранение дерева состава в
реляционной БД, версионирование со сменой состояний, расчёт массы изделия и построение
сводной спецификации. Интерфейс — десктопный (WPF, MVVM), вся предметная логика вынесена из UI.

Тестовое задание .NET: **«Мини-PDM: Состав изделия»**.

## Быстрый старт

Требуется .NET SDK 8.0+ и Docker (для PostgreSQL).

```bash
# 1. Поднять PostgreSQL
docker compose up -d

# 2. Собрать решение
dotnet build

# 3. Запустить тесты (модульные + сквозные на реальном PostgreSQL через Testcontainers)
dotnet test

# 4. Запустить приложение
dotnet run --project src/MiniPdm.Ui
```

Строка подключения по умолчанию:

```
Host=localhost;Port=5432;Database=minipdm;Username=minipdm;Password=minipdm
```

Её можно переопределить:
- переменной окружения `MINIPDM_CONNECTION`;
- файлом `src/MiniPdm.Ui/appsettings.json` (секция `ConnectionStrings:Postgres`).

Схема БД применяется автоматически при старте приложения (идемпотентный скрипт
`src/MiniPdm.Infrastructure/Database/Schema.sql`, встроенный ресурс) — отдельная миграция
вручную не нужна. Если Docker недоступен, приложение всё равно запустится и покажет
предупреждение, а интеграционные тесты будут пропущены.

## Архитектура

```
MiniPdm.slnx
├─ src/
│  ├─ MiniPdm.Domain          — сущности и инварианты (Designation, ObjectState, BomLink, ...)
│  ├─ MiniPdm.Application     — порты и сценарии (ICadDocumentReader, IPdmService, ImportService, расчёты)
│  ├─ MiniPdm.Cad             — адаптер формата: JsonCadDocumentReader, JsonCadSource
│  ├─ MiniPdm.Infrastructure  — PostgreSQL/Dapper, схема, экспорт CSV, часы
│  └─ MiniPdm.Ui              — WPF + MVVM + композиция Jab
└─ tests/
   └─ MiniPdm.Tests           — модульные и интеграционные тесты
```

Разделение по слоям (ports & adapters):

- **Domain** — `PdmObject`, `ObjectVersion`, `BomLink`, `ObjectType`, `ObjectState`,
  `ObjectStateMachine`, `Designation`. Вся валидация инвариантов Здесь.
- **Application** — порты `ICadDocumentReader`, `ICadSource`, `IImportStore`,
  `IPdmQueryRepository`, `IPdmCommandRepository`, `IDatabaseInitializer`,
  `ISpecificationExporter`, `IClock` и сценарии `ImportPlanner`, `ImportService`,
  `VersionService`, `MassCalculator`, `SpecificationBuilder`, `CycleDetector`;
  фасад `IPdmService`/`PdmService`.
- **Cad** — `JsonCadDocumentReader` (разбор одного файла) и `JsonCadSource` (перечисление
  `.a3d`/`.m3d`). Единственное место, знающее про JSON и файлы.
- **Infrastructure** — `NpgsqlConnectionFactory`, репозитории на Dapper, `PostgresImportStore`
  (транзакционный), `PostgresDatabaseInitializer`, `CsvSpecificationExporter`, `SystemClock`.
- **Ui** — `MainViewModel`, `PdmTreeNodeViewModel`, команды, конвертеры, `AppContainer`.

Ключевой приём — требование задания **«остальной код не знает про JSON/ФС»** — реализовано
через `ICadDocumentReader`/`ICadSource`: планировщик и сервисы оперируют доменными моделями,
а формат локализован в проекте `MiniPdm.Cad`.

## Доменная модель

### Типы объектов

| Тип | Обозначение | Масса | Материал | Идентификация |
|-----|-------------|-------|----------|---------------|
| `Assembly` (сборка) | обязательно, ЕСКД | рассчитывается по составу | — | по обозначению |
| `Part` (деталь) | обязательно, ЕСКД | обязательна | обязателен | по обозначению |
| `StandardPart` | отсутствует | обязательна | не требуется | по уникальному наименованию |

Обозначение по ЕСКД: `^[А-ЯЁ]{4}\.\d{6}\.\d{3}$` (4 заглавные кириллические буквы, 6 цифр,
3 цифры), уникально. У стандартных изделий обозначения нет, поэтому их ключ — наименование
(например, `Подшипник 206 ГОСТ 8338-75`).

### Версии и состояния

Версия имеет номер и состояние:

```
В работе ──► Утверждено ──► Аннулировано
      └──────────────────► Аннулировано
```

Переходы только «вперёд»; обратный переход запрещён (`ObjectStateMachine`). Текущей версией
объекта считается последняя **неаннулированная** версия. Связь «входит в» ведёт от
**версии-родителя** к **объекту-ребёнку** (не к версии): при расчёте берётся текущая версия
потомка, поэтому смена состояния/версии потомка автоматически отражается в составе родителя.

Повторный импорт (`VersionService`):
- данные не изменились → действий нет (`NoChange`);
- версия «В работе» → обновляем её;
- версия «Утверждено» → создаём новую версию «В работе».

## Схема базы данных

Полный скрипт — `src/MiniPdm.Infrastructure/Database/Schema.sql`.

```
pdm_object          — объект: id, object_type, designation (NULL для стандартных), name,
                      current_version_id → object_version(id)
object_version      — версия: id, object_id, version_no, state, material, mass_kg, created_at
                      UNIQUE(object_id, version_no)
bom_link            — состав: id, parent_version_id → object_version(id),
                      child_object_id → pdm_object(id), quantity > 0
                      UNIQUE(parent_version_id, child_object_id)
import_log          — журнал импорта: started_at, file_name, severity, reason
```

Ограничения целостности:

- частично-уникальный индекс по `designation` (только для не-NULL) — обозначение уникально;
- частично-уникальный индекс `object_type = 'StandardPart'` по `name` — уникальность
  стандартных изделий;
- `mass_kg >= 0`, `quantity > 0`;
- FK на текущую версию, каскадное удаление версий при удалении объекта.

Дерево состава читается **одним рекурсивным CTE** (`PdmQueryRepository.GetStructureAsync`):
запрос обходит `bom_link` сверху вниз, перемножая количества и собирая итоговое дерево за один
запрос к БД. Отдельный CTE с `CYCLE`-защитой используется/покрывается `CycleDetector` на
уровне приложения.

## Импорт CAD-папки

Конвейер: **чтение → валидация → разрешение ссылок → транзакционная запись**.

1. `JsonCadSource` перечисляет `.a3d`/`.m3d`, для каждого вызывая `JsonCadDocumentReader`.
   Ошибка одного файла не прерывает импорт — она превращается в запись отчёта.
2. `ImportPlanner` (чистая логика, без БД и ФС) выполняет:
   - валидацию полей (формат обозначения, обязательные материал/масса/наименование, тип);
   - поиск дублей обозначений и наименований стандартных изделий — **отклоняются все участники**;
   - проверку ссылок с **итеративным распространением отказов вверх**: если сборка ссылается
     на отклонённый/отсутствующий объект или `count ≤ 0`, сборка тоже отклоняется, и это уходит
     выше по дереву;
   - поиск циклов в графе ссылок (`CycleDetector`) — все сборки цикла отклоняются.
3. `PostgresImportStore.ApplyAsync` применяет план в **одной транзакции**, определяя для каждого
   объекта действие (`VersionAction`) и записывая состав и журнал импорта.

Правила отказов (см. также [принятые решения](#принятые-решения-и-неоднозначности)):

| Ситуация | Результат |
|----------|-----------|
| Битый JSON / нечитаемый файл | отклонение файла |
| Неверный формат обозначения | отклонение файла |
| Дубль обозначения (детали/сборки) | отклоняются все файлы с этим обозначением |
| Дубль наименования стандартного изделия | отклоняются все такие файлы |
| `count ≤ 0` у компонента | отклоняется сборка-родитель |
| Ссылка на отсутствующий/отклонённый объект | отклоняется сборка-родитель (рекурсивно вверх) |
| Цикл в составе | отклоняются все сборки цикла |
| Деталь без материала | отклонение файла |
| Отсутствует масса у детали/стандартного изделия | объект принимается, **предупреждение** |

## Расчёты: масса и спецификация

### Масса (`MassCalculator`)

- масса сборки = Σ (масса потомка × количество) по всему поддереву;
- если в поддереве есть узел без массы, результат — `null` (не ноль и не «частичная» сумма),
  а список `Missing` содержит проблемные позиции;
- при наличии цикла возвращается `HasCycle = true` и `TotalKg = null`.

Это осознанное решение: молча занижать массу опаснее, чем честно сообщить «не определено».

### Спецификация (`SpecificationBuilder`)

- плоский список всех деталей и стандартных изделий поддерева;
- количества перемножаются по пути и складываются по всем вхождениям;
- строки без массы выводятся с пустой массой, а не с нулём;
- сортировка по обозначению (или наименованию), затем по наименованию;
- при цикле спецификация не строится (`HasCycle = true`).

Экспорт готовой спецификации — в CSV (`;`-разделитель, UTF-8 BOM, совместимо с русским Excel).

## Интерфейс

WPF, MVVM, без логики в code-behind. Оформление — **WPF-UI 4.3** в стиле Windows 11
(Fluent/WinUI): `ui:FluentWindow` с `ui:TitleBar`, светлая Fluent-тема, контролы
`ui:Button`/`ui:TextBox`/`ui:SymbolIcon`/`ui:Card`/`ui:DataGrid`/`ui:ProgressRing`.

- **Поиск** по обозначению/наименованию — список результатов.
- **Карточка объекта**: обозначение, тип, текущая версия, состояние, материал, масса; список
  всех версий; кнопки **«Утвердить»/«Аннулировать»** (доступность по текущему состоянию).
- **Дерево состава** с **ленивой подгрузкой** узлов (по раскрытию).
- **Сводная спецификация** выбранного изделия с экспортом в CSV.
- **Импорт папки** с выбором каталога, прогресс-индикатором и возможностью **отмены**
  (`CancellationToken`); по завершении — **отчёт** (принято/отклонено/предупреждений и причины).

Композиция зависимостей — `AppContainer` (Jab, compile-time DI). `App` создаёт контейнер,
применяет схему и открывает окно; `MainWindow` получает `MainViewModel` через конструктор.

## Принятые решения и неоднозначности

Задание допускает трактовки; спорные места решены так:

1. **Масса при отсутствии данных.** Возвращается `null` + список проблемных позиций, а не 0 и
   не сумма «что нашлось». Иначе пользователь получил бы правдоподобное, но неверное число.
2. **Дубли обозначений.** Поскольку обозначение — ключ объекта, при коллизии отклоняются **все**
   конфликтующие файлы (нельзя выбрать «правильный» автоматически).
3. **Каскад отказов.** Отказ компонента отклоняет и все сборки, которые на него ссылаются
   (итеративно вверх), — иначе в БД попал бы «дырявый» состав.
4. **Циклы.** Все сборки цикла отклоняются целиком. Альтернатива (оборвать одну связь) молча
   теряет данные.
5. **Стандартные изделия.** Не имеют обозначения и материала; ключ — уникальное наименование;
   масса у них обязательна, но для устойчивости к «грязным» данным отсутствие массы даёт
   предупреждение, а не отказ.
6. **Тип `Part` без материала** считается ошибкой (материал — обязательный атрибут детали).
7. **Повторный импорт.** Сравнение версии «В работе» с новыми данными по составу/реквизитам;
   утверждённые версии не меняются — создаётся новая «В работе».
8. **Импорт одной транзакцией.** Либо применяется весь план, либо ничего; отчёт по каждому файлу
   сохраняется, включая причины отказов.
9. **`mass_kg` для сборок** в БД не хранится как атрибут — масса сборки всегда вычисляется по
   текущему составу (в JSON у сборок `mass: null`).

Решения по инфраструктуре: PostgreSQL вместо файловой/встраиваемой СУБД — ради рекурсивных CTE
и соответствия «нашему стеку»; Jab — чтобы DI проверялся компилятором; Dapper — чтобы дерево
читалось одним явным рекурсивным запросом.
